## 6. Recursos — Host (vmstat)

> **Glossario:**
> - **CPU us (user):** % de CPU gasta em codigo de usuario (processos normais, incluindo os bancos).
> - **CPU sy (system):** % de CPU gasta em kernel (syscalls, I/O scheduling).
> - **CPU id (idle):** % de CPU ociosa. CPU total usado = 100 - idle.
> - **IO wait (wa):** % de CPU parada esperando disco. Se alto (>10%), o disco e o gargalo.
> - **bi (blocks in):** Blocos lidos do disco por segundo. Mede leitura de disco real. Alto bi = cache insuficiente.
> - **bo (blocks out):** Blocos escritos no disco por segundo.
> - **Run queue (r):** Processos na fila de CPU. Se > numero de nucleos, CPU esta sobrecarregada.

## 7. Verdicto

### Quem teve mais throughput? (RPS)
**PostgreSQL** — 47,33 RPS vs 32,81 RPS do MariaDB. O PostgreSQL processou **44% mais requisicoes por segundo** no mesmo periodo.

### Quem teve menor latencia mediana? (p50)
**PostgreSQL** — 800ms vs 9.800ms do MariaDB. A experiencia "tipica" do usuario e **12x mais rapida** no PostgreSQL.

### Quem teve menor latencia no p95 e p99? (cauda)
**MariaDB** — p95 de 15.000ms vs 20.000ms do PostgreSQL, e p99 de 16.000ms vs 32.000ms. O MariaDB entrega latencia **mais previsivel** — todas as requisicoes convergem para o mesmo teto de ~15s, enquanto o PostgreSQL tem caudas longas chegando a 62s.

### Quem consumiu mais CPU?
**MariaDB** — container a 197,81% medio vs 60,13% do PostgreSQL (3,3x mais). O host teve 42,51% de CPU(us+sy) medio no teste MariaDB vs 19,42% no PostgreSQL.

### Quem fez mais IO de disco?
**MariaDB** — 389 blocos/s medio de leitura vs 1 bloco/s do PostgreSQL. O InnoDB leu disco para preencher o buffer pool; o PostgreSQL usou exclusivamente o page cache do SO.

### Qual foi o MAIS PERFORMATICO neste cenario e por que?
**PostgreSQL foi mais performatico em throughput e latencia mediana**, processando 44% mais requisicoes com p50 12x menor. A vantagem vem da arquitetura de **cache duplo** (shared_buffers + page cache do SO): o dataset de 340k registros cabe inteiro na RAM do host via page cache, eliminando praticamente toda leitura de disco e reduzindo drasticamente o uso de CPU.

**Porem**, o PostgreSQL apresenta **caudas longas** (p99 de 32s, max de 63s) — algumas requisicoes sofrem latencias extremas quando o SO precisa liberar paginas do cache ou quando ha contenção de conexoes. O MariaDB, embora mais lento na mediana, tem uma **latencia muito mais previsivel** (p99 de 16s, max de 21s).

**Resumo:** PostgreSQL vence em velocidade bruta e eficiencia de recursos. MariaDB vence em consistencia/predictabilidade de latencia sob carga extrema (500 usuarios simultaneos).

## 8. Observacoes

1. **Zero falhas em ambos os bancos** — Nenhum timeout, erro HTTP ou excecao durante os 2 testes. Ambos os sistemas se mantiveram estaveis sob 500 usuarios simultaneos.

2. **P95 uniforme do MariaDB** — O fato de todos os endpoints terem p95 = 15.000ms sugere um **gargalo de CPU/conexao** no MariaDB: o pool de conexoes (max 20) ou o limite de threads do InnoDB saturam, criando uma fila uniforme. Aumentar `DB_POOL_MAX` ou `innodb_thread_concurrency` pode ajudar.

3. **Caudas longas do PostgreSQL** — O p99 de 32-40s em alguns endpoints indica que, embora o PostgreSQL responda a maioria das requisicoes em <1s, algumas enfrentam latencias extremas. Isso pode ser causado por:
   - Page cache do SO sendo liberado para outros processos (o container ocioso do MariaDB consome RAM)
   - Contencao no pool de conexoes asyncpg (max 20)
   - VACUUM ou checkpoint disparando durante o teste

4. **Diferenca de RAM livre** — O host terminou com 1.362 MB livres apos o teste PostgreSQL vs 1.573 MB apos o MariaDB. Isso porque o PostgreSQL cresce o page cache do SO durante o teste, reduzindo a RAM "livre" (mas essa RAM esta sendo usada como cache, nao desperdicada).

5. **Pico de leitura no MariaDB** — O pico de 77.824 blocos/s (≈38 MB/s) ocorreu nos primeiros segundos do teste (warm-up do buffer pool). Apos o buffer pool aquecer (≈30s), as leituras caem para <100 blocos/s.

6. **Container ocioso confirmado** — Durante cada teste, o container do banco nao testado ficou com 0,01% CPU, confirmando que a carga foi exclusiva ao banco sob teste.

7. **Tempo de teste curto (2 min)** — 120s e suficiente para atingir 500 usuarios e estabilizar, mas testes mais longos (5-10 min) dariam uma visao melhor das caudas longas do PostgreSQL e do comportamento do buffer pool do MariaDB apos fully warmed.
